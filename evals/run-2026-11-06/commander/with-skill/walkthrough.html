Codebase walkthrough

    Commander.js, from parse() to your action handler

    You declare a program's commands and options in code. Commander turns process.argv into option values, then calls your action or prints help or an error.

    tj/commander.jsat ba6d13darea: index.js, lib/ (6 files, about 4,180 lines), typings/, tests/~25 min read

    The big picture

    Commander is the argument parser behind a large number of Node.js CLIs. A CLI author builds a tree of Command objects, each with Options and Arguments, and calls program.parse(). Commander works out which subcommand was meant, fills in option values, checks for mistakes, and calls the .action() handler. It also writes the --help text and the error messages. Without it, every CLI author would hand-roll process.argv slicing, help text and "unknown option" errors.

    The package has zero production dependencies (package.json has only devDependencies), and the maintainers want to keep it that way (CONTRIBUTING.md, last paragraph). Almost all logic lives in one class, Command, in lib/command.js (2,790 lines).

    Like you're five

    Think of a restaurant order form. Before the restaurant opens, the owner prints the form: which dishes exist (subcommands), which boxes you can tick (boolean options), and which blanks you fill in (options with a value and command-arguments). A customer hands in a scribbled note (process.argv). The clerk (parse()) reads the note word by word. A word that names a tick box goes onto the form (an option: event sets the value). A word that names a dish sends the note to that dish's own clerk (_dispatchSubcommand). Whatever is left fills the blanks in order (_processArguments). Then the kitchen cooks (.action()). A tick box that does not exist gets the note handed back with an error. So does a missing required blank (error() then process.exit). Asking for the menu gets you the menu (Help.formatHelp).

    Where the analogy breaks: the clerk does not read the whole note before deciding. Each command reads only the words it knows, and passes everything after the first unknown one to the subcommand's clerk.

    Glossary

    The repo defines its own vocabulary in docs/terminology.md. Use these words in issues and PRs; maintainers do.

    Command
    A program or subcommand. It holds options, registeredArguments, commands (children) and parent. It is also an EventEmitter. Defined at lib/command.js:14.
    option
    A -x or --long token. Represented by Option, built from a flags string like '-c, --colour <shade>' in lib/option.js:11.
    option-argument
    The value an option takes. <x> means required (option.required), [x] means optional (option.optional), and x... means variadic. These are read from the flags string at lib/option.js:15.
    command-argument
    A positional value such as <size>. Represented by Argument (lib/argument.js:3). The code also calls these operands.
    operands / unknown
    The two buckets parseOptions() returns. Operands are non-option words seen before the first unknown option. Unknown is that first unknown option plus everything after it (lib/command.js:1760).
    attributeName()
    The camelCase key an option's value is stored under, with any no- prefix removed. --dry-run becomes dryRun (lib/option.js:217).
    value source
    Where an option's value came from: 'default', 'env', 'cli', 'implied', 'config'. It is stored next to the value and decides what may overwrite what (lib/command.js:944).
    parseArg
    A custom function (value, previous) => newValue on an Option or Argument. .choices() and .argParser() both set it (lib/option.js:132).
    CommanderError
    The error carrying exitCode and a code like 'commander.unknownOption'. It is thrown instead of exiting when .exitOverride() is set (lib/error.js:4).
    Help
    The class that builds help text. Every method is public so authors can override it with .configureHelp() (lib/help.js:13).

    The main flow: one real invocation

    Here is the program used in the trace below. It reuses the --colour option from tests/options.choices.test.js:7 and adds a subcommand. It was run against this commit in a scratch copy, and the outputs shown are real.

    const program = new Command('pizza');
program.command('order <size>')
  .addOption(new Option('--colour <shade>').choices(['red', 'blue']))
  .option('-d, --debug')
  .action((size, opts) => console.log('ACTION', size, JSON.stringify(opts)));
program.parse(process.argv.slice(2), { from: 'user' });
    1. pizza order large -d --colour red. parse() saves or restores state, then _prepareUserArgs (lib/command.js:992) uses from: 'user' to keep all four words as user args.
    2. program._parseCommand([], ['order','large','-d','--colour','red']) calls parseOptions. The program has no option named order, so order and large go to operands. -d is not a program option, so it and everything after it go to unknown (lib/command.js:1871).
    3. _findCommand('order') matches (lib/command.js:1570). _dispatchSubcommand calls order._parseCommand(['large'], ['-d','--colour','red']) (lib/command.js:1364).
    4. The child's parseOptions recognises -d and emits option:debug with no value. It recognises --colour as required, takes the next word and emits option:colour with 'red' (lib/command.js:1808).
    5. The listener from addOption runs parseArg. For .choices() that checks the allow-list. It then stores colour='red' with source 'cli'. debug has no value, so it becomes true (lib/command.js:699).
    6. Env vars, implied values, mandatory options and conflicts are applied and checked (lib/command.js:1564, lib/command.js:1598).
    7. _processArguments maps ['large'] onto the declared <size> (lib/command.js:1440). The action wrapper calls fn('large', {debug: true, colour: 'red'}, cmd). Real output: ACTION large {"debug":true,"colour":"red"}, exit 0.

    Where it can fail

    • Invalid value. With --colour orange, parseArg throws InvalidArgumentError. _callParseArg (lib/command.js:600) prefixes the message, and error() exits 1. Real output: error: option '--colour <shade>' argument 'orange' is invalid. Allowed choices are red, blue.
    • Unknown option or command. unknownOption (lib/command.js:2126) and unknownCommand (lib/command.js:2176) build the message, including a "Did you mean" hint from lib/suggestSimilar.js.
    • Missing argument. _checkNumberOfArguments (lib/command.js:1415) calls missingArgument, or _excessArguments when there are too many.

    Code tour, in reading order

    1. The entry point is tiny

    What it does: index.js creates the shared program singleton and re-exports the classes.

    Why it's built this way

    The package switched to ESM only in f4bd470 ("Switching to esm-only (#2464)"). package.json sets "type": "module", and exports points types at typings/index.d.ts. The typings are hand-written, not generated, so any public API change has to be mirrored there by hand.

    2. parse() is three calls

    What it does: it resets state, works out which argv entries are user args, and starts the recursive parse at the root.

    Why it's built this way

    _prepareForParse (lib/command.js:1118) saves state on the first parse and restores it on later ones. This came from 49423a2 ("Add save/restore state to allow multiple calls to parse"). Without it, calling parse() twice on one program would leak option values from the first call. parseAsync is the same three calls with await, for async action handlers.

    3. _parseCommand: the per-command loop

    What it does: it parses this command's own options, applies env and implied values, then either hands off to a subcommand or runs this command's action.

    The rest of the method (to lib/command.js:1653) is a decision ladder. It tries the help command, then the default command, then "has subcommands but none given, so show help". After that come the mandatory and conflict checks, and finally the action. When a command has no action it falls through (lib/command.js:1651), so a plain program.parse(); program.opts() script still works.

    Why it's built this way

    Env values are applied after CLI values so that parseArg is not called on both (comment at lib/command.js:1564). The order of the ladder sets which error a user sees first. The comment at lib/command.js:1601 says the unknown-option check is deferred "to avoid masking a 'better' error, like unknown command".

    4. parseOptions: classify each token

    What it does: it walks the args once. A known option emits an option:<name> event, and every other word goes to operands or unknown.

    After this block the loop also handles -abc short-flag groups, -cred (a value glued to a short flag) and --colour=red (lib/command.js:1851). It also handles -- (stop parsing), negative numbers, and the enablePositionalOptions and passThroughOptions modes.

    Why it's built this way

    Using events lets parseOptions stay ignorant of how values are stored or converted. Storing values belongs to whoever registered the listener, which is addOption. parseOptions is also public and tested on its own in tests/command.parseOptions.test.js. (inferred)

    5. addOption: where a value becomes a value

    What it does: it registers the option, stores any default, and subscribes a handler that applies preset, parseArg or variadic collection, then stores the result with its source.

    Like you're five

    Every value has a sticky note saying who wrote it: default, env, or cli. An env var may only overwrite a value whose note says default, config or env, never cli (lib/command.js:1983).

    Why it's built this way

    One handler serves both the CLI (option:) and env (optionEnv:) events, and only the error message and source differ (lib/command.js:716). .option() and .requiredOption() both go through _optionEx into this same method (lib/command.js:732). So addOption is the one place every option passes through.

    6. Option: a plain bag of settings

    What it does: the constructor reads the flags string. Each chainable method (default, preset, env, choices, conflicts, implies, ...) sets one field and returns this.

    Why it's built this way

    choices is built on top of parseArg instead of adding a separate validation step. That is why the error comes out through _callParseArg and reads like any other invalid value. It copies the array (values.slice()) because the TypeScript signature promises readonly string[] (typings/index.d.ts:184). Three tests guard that promise (tests/options.choices.test.js:27).

    7. Errors funnel through error() and _exit()

    What it does: it writes the message to stderr, optionally shows help, then exits. Exiting means calling the exitOverride callback if one is set, and process.exit otherwise.

    Why it's built this way

    A library that calls process.exit is hard to embed or test. exitOverride is the escape hatch, and the "Expecting this line is not reached" comment shows the callback is expected to throw. Only errors whose code is 'commander.invalidArgument' are turned into friendly messages. Any other exception from a parseArg is rethrown as is.

    8. The action wrapper and hooks

    What it does: after arguments are processed, it runs preAction hooks, then your handler, then postAction. It chains promises only if something returned one.

    Like you're five

    _chainOrCall (lib/command.js:1493) is "do it now, unless someone handed me a promise, then do it after". So a sync program stays fully sync, and parse() returns before anything async finishes. Use parseAsync() when actions are async.

    Why it's built this way

    Your handler receives (arg1..argN, opts, command). It gets exactly as many positional values as there are declared arguments, then the options object, then the command (lib/command.js:560). Extra words are not passed in. They are still on command.args.

    9. Help is a separate, overridable class

    What it does: helpInformation() (lib/command.js:2464) builds a Help, and formatHelp (lib/help.js:444) asks it for visible options, terms and descriptions, then lays out the columns.

    That is where (choices: "red", "blue") in the real help output comes from:

    Usage: pizza order [options] <size>

Options:
  --colour <shade>  (choices: "red", "blue")
  -d, --debug
  -h, --help        display help for command
    Why it's built this way

    Every Help method is public and small (optionTerm, optionDescription, styleTitle, ...). Authors can replace one piece through .configureHelp({...}) without forking the layout. Each method has its own test file (tests/help.*.test.js). The depth guide is docs/help-in-depth.md.

    10. Tests: node:test plus a helper

    What it does: most tests build a command with createTestCommand(), call parse([...], { from: 'user' }), and assert on opts() or on a thrown error.

    Conventions that apply here

    • Open PRs against develop, not master (CONTRIBUTING.md, Pull Requests).
    • Do not edit CHANGELOG.md or the version. Maintainers do that at release (CONTRIBUTING.md). Put a suggested CHANGELOG line in the PR description instead.
    • Update all the documentation a change touches: TypeScript typings, JSDoc in the code, tests, README and examples/. The same list is in CONTRIBUTING.md. It is fine to open the code first and ask before doing the rest.
    • No new runtime dependencies. Such PRs are "much less likely to be accepted" (CONTRIBUTING.md).
    • Style is enforced by Prettier and ESLint (eslint.config.js, .editorconfig). Run npm run fix rather than formatting by hand.
    • JSDoc types are checked. check:type:js runs tsc -p tsconfig.js.json over the JS, so the @param/@return tags must be correct. Helpers that should stay out of the public API are marked @private or @package.
    • Test names read as 'when X then Y' inside a describe('Class.method()') block (see tests/options.choices.test.js:7).

    Recipe: add another Option modifier like .choices() or .env()

    1. lib/option.js: add a field with its default in the constructor (lib/option.js:11). Add a chainable method with JSDoc that sets it and returns this, next to its siblings (lib/option.js:65 to lib/option.js:181).
    2. lib/command.js: use the field where it takes effect. Value transforms go in handleOptionValue inside addOption (lib/command.js:683). Whole-command checks go next to _checkForMissingMandatoryOptions and _checkForConflictingOptions, which are called at lib/command.js:1598. Report errors through this.error(message, { code: 'commander.<name>' }) so exitOverride works.
    3. lib/help.js: if users should see the setting, add it to the extraInfo list in optionDescription (lib/help.js:326).
    4. typings/index.d.ts: declare the method on class Option (typings/index.d.ts:95), with the same JSDoc. Add expectType lines to typings/index.test-d.ts (see the choices block at typings/index.test-d.ts:719).
    5. tests/options.<feature>.test.js: a new file using createTestCommand(). Add an error-code test in tests/command.exitOverride.test.js if you added an error.
    6. Docs: Readme.md and docs/options-in-depth.md, plus an examples/ file if it helps.
    7. Run npm test and npm run check, then open the PR against develop.

    For an Argument modifier, the same steps apply with lib/argument.js, _processArguments (lib/command.js:1440), argumentDescription in lib/help.js:373, and class Argument at typings/index.d.ts:48.

    Watch out
    • Events use name(), storage uses attributeName(). The event for --dry-run is option:dry-run, but the value is stored as dryRun (lib/command.js:674). A negated --no-color stores under color.
    • parse() can run more than once. Any new per-parse state on Command must be saved and restored in saveStateBeforeParse and restoreStateBeforeParse (lib/command.js:1154), or it leaks between parses.
    • Tests that hit an error path without exitOverride() call the real process.exit and kill the runner. Use createTestCommand().
    • Check order is visible to users. Moving a check in _parseCommand changes which error people see when there are two problems. Keep "unknown command" ahead of "unknown option" (lib/command.js:1601).
    • Typings drift silently from the JS. tsd only checks what index.test-d.ts exercises.
    • Executable subcommands (.command('name', 'description') with no action) spawn a separate process (lib/command.js:1215). Behaviour there differs by platform. CI runs on Windows for this reason (inferred).

    Check yourself

    A user runs tool --colour=orange. Which function rejects it, and what prefix does the error message get?

    The --x=y branch of parseOptions (lib/command.js:1851) emits option:colour with 'orange'. handleOptionValue calls _callParseArg, the .choices() parseArg throws InvalidArgumentError, and _callParseArg prefixes it with error: option '--colour <shade>' argument 'orange' is invalid.. See code-tour stops 4 to 7.

    Why does the parent program not complain about -d in pizza order large -d?

    The parent's parseOptions puts the first unknown option and everything after it into unknown, not into an error. _parseCommand finds order in operands and hands unknown to the child before any unknown-option check runs. See the main-flow trace, steps 2 and 3.

    You add a new field to Command that parseOptions writes. What else must you touch so a second parse() works?

    saveStateBeforeParse and restoreStateBeforeParse at lib/command.js:1154. See the Watch out list.

    Your new test fails with the runner exiting instead of an assertion. What did you forget?

    .exitOverride(). Build the command with createTestCommand() from tests/testHelpers.js:12 so _exit throws a CommanderError instead of calling process.exit. See code-tour stops 7 and 10.

    You added Option.prototype.foo() and npm test passes. What will the maintainers still ask for?

    A declaration in typings/index.d.ts, expectType lines in typings/index.test-d.ts, README/docs updates, and npm run check passing. Not a CHANGELOG edit. See the Conventions and Recipe blocks.
